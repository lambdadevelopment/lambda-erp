# General activity feed, including chat and MCP

Status: **deferred; not implemented**. Updated 2026-09-15.

The first implementation uses [shared list time filters](time-filters.md),
without an aggregate endpoint/event table. The design below is retained for
future audit/history requirements, not part of the current implementation.
Scope: ERP core; customer plugins can extend the same mechanism.

## Outcome

Answer questions such as “What happened in the last 24 hours?”, “What did John
change today?”, and “Who assigned the asset on RES-0017?” from persisted business
events. REST, the ERP chat, the programmatic chat API, and MCP must expose the
same authorized information. Chat integration is part of the first complete
implementation, not a later enhancement.

An activity is a successful business change: a document created, modified,
submitted, cancelled or discarded; a master changed or deleted; a reservation
reassigned; a reconciliation completed; or a plugin action such as a lead merge.
Start with compact structured events in the existing database. No separate
queue, logging service, or LLM call is needed to record them.

## Current seams and gaps

- `api/routers/reports.py::_dashboard_summary` lists recent creations for five
  document types. It cannot reconstruct changes or provide a complete period.
- `lambda_erp/model.py` centralizes document save/submit/cancel/discard, but
  `db.set_value` and direct SQL bypass that lifecycle.
- `api/routers/masters.py` owns additional master CRUD paths; registered actions,
  imports, reconciliation and jobs also have their own write boundaries.
- The generic hook documentation and actual transaction boundaries need care:
  `save()` currently runs `after_save` inside its atomic block, whereas
  `after_submit` and `after_cancel` run outside their local atomic blocks.
  Implement activity writes inside the actual business transaction. Registering
  a generic `after_*` callback is insufficient.
- Chat tool schemas/handlers live in `api/chat.py`; role classification lives in
  `api/tool_permissions.py`. MCP reuses these schemas but has its own caller-aware
  dispatch in `api/routers/mcp.py`. `/api/v1/chat` uses the shared chat turn runner.
- ERP-internal already has a lead-specific `Activity` doctype. Keep that CRM
  timeline and its business rules; add an extension adapter to the general feed.

## Storage and event semantics

Add an append-only internal `Activity Event` table through a new core migration,
portable across SQLite and PostgreSQL. Do not expose its writes through generic
document/master CRUD. Proposed fields:

| Field | Purpose |
| --- | --- |
| `id` | Server-generated event UUID |
| `recorded_at` | UTC time the business change was recorded |
| `actor_type`, `actor_id` | Authenticated user or explicitly identified system job |
| `source` | Trusted execution channel: REST, chat, chat API, MCP, job or core |
| `action` | Stable action code, e.g. `created`, `updated`, `submitted`, `merged` |
| `doctype`, `document_name` | Primary affected record, retained after deletion |
| `company` | Scope where applicable; null has explicit global-record semantics |
| `summary` | Bounded, deterministic description; generated by application code |
| `changes_json` | Bounded allowlisted changes, including relevant child-row changes |
| `operation_id` | Groups events caused by one business operation |
| `metadata_json` | Versioned, bounded related-record references and plugin metadata |

Index `(recorded_at, id)`, `(actor_id, recorded_at)`,
`(doctype, document_name, recorded_at)`, and `(company, recorded_at)`.

Use `recorded_at` for “last 24 hours”. A backdated invoice or imported CRM note
must appear when it is recorded; its business/interaction date can be separate
metadata. Do not populate the activity timestamp from a document's posting date.

Record actual persisted changes, not the submitted request body. Exclude secrets,
tokens, full chat transcripts, attachments and unrestricted document snapshots.
Allowlist useful values such as reservation asset references and status changes;
for sensitive text, a field-changed indication can suffice. Apply read permissions
to descriptions and diffs as well as to record links. Bound payload size and mark
omitted detail explicitly.

## Capture and transaction guarantees

1. Add a framework-independent recording helper in the core, using the current
   database transaction. Include the event before commit; a recording failure
   rolls back the associated business change. A rolled-back operation produces
   no success event. Recording must never issue an independent commit.
2. Carry actor/source/operation context from authenticated entry points into the
   shared writers. Use scoped context that is reset on exit and propagated into
   worker execution. Never accept actor identity from document fields, LLM tool
   arguments or an untrusted header. Jobs identify themselves explicitly; retain
   the initiating user where known. Correlation IDs do not replace idempotency.
3. Instrument the document lifecycle and master CRUD, including the alternate
   plugin master/document paths. Capture deletion identity and scope before the
   row disappears. Skip updates that change only bookkeeping timestamps.
4. Inventory special actions and direct database writers before claiming complete
   coverage: conversions, merges, stock workflows, bank import/reconciliation/
   undo, payment/order progress, setup actions, recurring billing, background
   imports and plugin jobs. Each path must have an explicit recording boundary
   or a documented inclusion in its parent business event.
5. Group causal changes under one operation. Avoid counting a submitted invoice
   plus its individual GL/stock rows as unrelated user actions. Existing retry
   and idempotency mechanisms must not generate duplicate success events for an
   already completed operation. An operation with independently committed batch
   items records successful items even when other items fail.
6. Provide an extension registration seam for event codes, safe changes,
   visibility and links. Unknown plugin event types are hidden until a read
   policy exists. For internal CRM, bridge notes, contacts, status changes and
   merges, avoiding duplicate generic and semantic events for the same change.
7. Do not capture the activity table's own inserts. Keep technical errors, reads
   and logins outside this initial business feed. Retain their existing logs.

A write-path coverage checklist is a required implementation artifact. Extend it
when adding new core or plugin write paths. Mark unsupported coverage explicitly;
do not silently equate “nothing recorded” with “nothing happened”.

## Shared read service and REST contract

Proposed endpoint: `GET /api/activity?hours=24`.

- Accept either `hours` (default 24) or explicit timezone-aware `since`/`until`.
  Reject conflicting or invalid ranges. Resolve and return a fixed UTC window;
  support local calendar periods by converting the user's stated timezone.
- Filters: actor, company, doctype, document name, action, source and operation.
- Use deterministic keyset pagination on `(recorded_at, id)` with the fixed time
  window carried into the cursor. Default page size 50, maximum 200; bound query
  windows and reject invalid cursors/filters rather than silently broadening them.
- Return `events`, `next_cursor`, `has_more`, the resolved window, visible total
  event count, and authorized summary counts by action/type. Distinguish events,
  operations and affected records so a summary cannot confuse these counts.
- Include coverage metadata: capture start, supported event families, known gaps
  and earliest retained time. History before activation is not complete. Do not
  synthesize historical changes from current `modified` timestamps.
- Use one read service for REST and tools. Enforce the caller's resource and
  company access before pagination and aggregation, including counts and links.
  A user-supplied company filter is not authorization. Reuse the ERP's actual
  read rules; add shared policy helpers where existing routes enforce them
  separately. Preserve safe scope checks for deleted records.
- Proposed roles: authenticated viewer/manager/admin, constrained by underlying
  record permissions. Exclude the shared `public_manager` demo identity from the
  general feed. API-key access must respect the existing REST/MCP switches.

Do not add an arbitrary SQL analytics path for this endpoint. Event storage must
also be excluded from any generic document/dataset surface that could bypass its
read policy. No automatic destructive retention purge in the initial release;
document retention as a deployment setting and report gaps if later enabled.

## Mandatory chat, prompt and MCP integration

Add one read tool, `list_activity`, backed by the same read service and query
contract. Its response includes authorized aggregate counts and bounded event
details, so a normal daily overview does not require loading the entire history.

- Register schema, description, handler and explicit role policy in
  `api/chat.py` and `api/tool_permissions.py`.
- Bind the authenticated caller in both the chat runner and MCP dispatch.
  Shared schema discovery alone does not supply caller context or permissions.
- Verify availability in browser chat, stateful and stateless `/api/v1/chat`,
  and MCP `tools/list` / `tools/call`. Programmatic chat inherits the tool through
  the shared runner; respect each surface's existing authentication/settings.
- Update the ERP system prompt and tool description to call `list_activity` for
  recent-activity, actor-history and record-change questions. Describe supported
  actions, filters and the difference between capture time and business date.
- Resolve “today”/“yesterday” in the user's known timezone; use `get_current_time`
  as needed. Ask for timezone if it materially changes an otherwise unknown
  calendar window. Rolling 24 hours means the preceding 24 elapsed hours.
- Explain the covered period and relevant limits in the answer. Use full-window
  authorized counts for totals, not page length. Follow pagination for requested
  detail; never describe a truncated page as an exhaustive list.
- Empty complete coverage means no recorded matching activity. Partial coverage,
  unavailable capture or a query error must be reported as such, not as zero
  activity. The model must not infer missing events from current document state.
- Include record references and navigation only where supported. Treat event
  descriptions and user-entered values as data, not instructions to the model.

Keep the tool description available to external MCP clients. Document the new
capability in `docs/chat-api.md` and `docs/rest-api.md`; verify the Lambda-web
connector can use it through its existing ERP chat/MCP integration. Any connector
with a fixed capability list needs a corresponding description update.

## Implementation sequence and acceptance

- [ ] **Coverage/design:** enumerate writers and permissions, finalize event
  codes/grouping, and specify the extension contract. Resolve transaction-boundary
  discrepancies against actual code before choosing instrumentation points.
- [ ] **Capture:** migration, indexes, actor context, transactional recording,
  lifecycle/master coverage and special workflow integration.
- [ ] **Read + LLM:** shared permission-aware query service, REST endpoint,
  `list_activity`, caller-aware dispatch, prompt guidance and API documentation.
  Capture alone is not the completed feature.
- [ ] **Extensions and rollout:** internal CRM adapter, background-job coverage,
  connector capability check, coverage metadata and migration on existing data.
  Validate on Develop before production; choose release version when shipping.

Required checks on SQLite and PostgreSQL:

- Correct actor and source across REST, browser chat, chat API, MCP and jobs;
  no actor leakage across requests/workers and no forged actor fields.
- Document/master creates and meaningful edits; submit/cancel/discard/delete;
  asset reassignment, conversion, merge, stock posting and reconciliation/undo.
- Commit/rollback consistency, including event-insert failures, nested workflow
  failures, retries, no-op updates and partially successful batches.
- Plugin alternate write paths and CRM semantic events are captured once; large
  imports stay bounded and do not multiply ledger rows into user-level actions.
- Same records/counts/field visibility on all read surfaces; denied/private,
  cross-company, deleted-record, unknown-plugin and public-demo cases.
- UTC/calendar/DST boundaries, fixed query windows, cursor ties, pagination,
  truncation, capture-start/retention gaps and empty/error distinctions.
- Tool discovery and real dispatch tests for browser chat, chat API and MCP,
  plus representative prompt evaluations: “last 24 hours”, “John today”,
  “who changed RES-0017's asset?”, no results and incomplete history.
- Existing full ERP validation suite remains green; inspect query plans and
  exercise a realistic import volume to check write overhead and read latency.

A dedicated activity-feed UI can follow independently. REST and LLM access,
correct attribution and explicit coverage are required for the initial delivery.
